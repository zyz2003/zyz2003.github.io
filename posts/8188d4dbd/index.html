问题来源

最近有一个新的需求，需要在用户的企微里面集成一个智能机器人，用于回答用户的问题，包括一些日常办公的自动化操作。

企业微信现有的机器人功能有两种：

  • 应用模式
  • 智能机器人模式

两种模式都有各自的优势和限制。但智能机器人模式更符合用户需求，因为它：

  • 可以直接在企微里面与用户交互
  • 可以添加到群聊，支持单聊、多聊
  • 支持流式回复，支持卡片、图片等格式

然而，企微自带的模型+数据集+提示词模式不能满足多样化需求，需要通过第三方智能体API（如dify、coze、n8n）进行回复。但主流智能体平台的API格式与企微不兼容，需要用Java或Python进行桥接通信。

回复模式

交互格式均为JSON，官方提供两种回复模式：

1. 被动回复

  • 企微向桥接项目发送POST请求，请求体需先解密
  • 解密前是键值对：键为encrypt，值为加密后的请求体
  • 使用企业微信智能机器人的appsecret作为密钥，进行AES-128-CBC解密

2. 主动回复

主动回复与被动回复流程基本相同，但分两次请求：

  • 企微将交互事件回调到设置的回调URL，返回response_url
  • 处理完业务逻辑后，使用response_url主动调用接口回复消息

注意：主动回复有很大局限性，不支持流式，只有Markdown格式的回复。

踩坑记录

1. NullPointerException问题

问题：在处理Dify SSE事件时，尝试访问JSON字段（如user）时抛出NullPointerException

  • 原因：代码中直接调用jsonNode.get("user").asText()，未检查user字段是否存在
  • 解决方案：在访问JSON字段前添加null检查，使用jsonNode.has("user")判断字段是否存在

2. 40008无效的消息类型问题

问题：主动回复消息时，返回40008错误码，提示"无效的消息类型"

  • 原因：主动回复消息格式与被动回复不同，需按官方文档组装正确格式
  • 解决方案：
    • 组装正确的JSON字符串，包含msgtype和text字段
    • text字段中包含content字段，为回复的文本内容
    • 注意：主动回复无需加密，被动回复需要加密
    • 格式为JSON，不是XML

3. 连续微信刷新请求问题

问题：微信机器人持续发送刷新请求，导致系统资源浪费（启用流式回复时的问题）

  • 原因：系统没有正确处理Dify的message_end事件，而是在普通message事件中过早标记任务为完成
  • 解决方案：
    • 移除handleMessageEvent方法中所有标记任务为完成的逻辑
    • 确保只有当收到Dify的message_end事件时，才将任务标记为完成
    • 这样微信收到finish=true的响应后，就会停止发送刷新请求

关键实现点

1. 企微智能机器人的流式回复实现

实现方式：基于Dify SSE（Server-Sent Events）API和企微机器人的流式刷新机制

核心逻辑：

  • 用户发送消息 → 服务端调用Dify SSE API → 异步处理SSE事件流 → 企微定期发送刷新请求 → 服务端返回当前内容和状态 → 直到流式结束

2. 流式回复的核心组件

组件 作用
DifyService 处理SSE事件流，管理流式任务状态
RobotMessageService 处理企微消息，响应流式刷新请求
StreamTask 存储流式任务状态，包括当前内容、完成状态等

3. Dify SSE API在流式回复中的作用

  • 提供实时的流式回复数据
  • 通过不同类型的事件（message/message_end）通知服务端
  • 传递对话ID和消息ID，用于上下文管理

4. 企微的流式刷新机制

刷新机制：

  • 企微机器人会定期发送stream类型的请求
  • 每次请求携带stream_id，用于获取对应流式任务的最新状态
  • 服务端返回当前内容和finish状态
  • 当finish: true时，企微停止刷新

  • 正确处理Dify的message_end事件
  • 当收到message_end事件时，将流式任务的isFinished标记为true
